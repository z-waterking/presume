# 复习笔记 — 阿里推荐系统

> 2026-04-13 复习整理

---

## 一句话总结

> 排序靠人调权、召回靠人拍配额、上下游耦合马太效应 → 三件事：**PID 自动调权排序** / **Borda Count 动态融合召回** / **全链路评估解耦**。

---

## 痛点

1. **排序权重调不动**: LTR 上线后参数固定，业务目标（冲GMV/推新品/保UV）是动态的，人工调权一个循环要好几天
2. **召回配额太僵化**: 10+路召回每路取多少是人工拍的（I2I取50, U2I取50），低效源占坑高效进不来，马太效应
3. **上下游耦合**: 召回模型的正样本来自精排胜出日志 → 精排不喜欢的永远不被召回 → 马太效应 Loop

---

## 第一件事: PID 控制器做排序动态调权

### 核心思想

借鉴自动控制 PID，把推荐排序变成**闭环反馈系统**：

```text
业务目标（如UV价值=X）
        │
        ▼
  误差计算: Error = 目标值 - 实际线上指标
        │
        ▼
  PID 控制器: 输出 = P×误差 + I×累积误差 + D×误差变化率
        │
        ▼
  调整 LTR Loss 权重 / Ranking Score 加权
        │
        ▼
  线上排序结果 ──反馈──▶ 回到误差计算
```

运营只需设定目标值，系统自动寻优。

### P / I / D 业务含义

- **P（比例）**: 当前误差直接反应。GMV偏低5% → 立即加大GMV权重
- **I（积分）**: 累积误差修正。GMV持续偏低 → 逐步加大力度，消除**稳态误差**
- **D（微分）**: 误差变化趋势预判。偏差在缩小 → 提前减小力度，防止**过冲**
- 实际主要依赖 **PI**，D项做低通滤波

### PID vs 手动调权的本质区别

> "手动调权是**开环控制**——人看到指标不对，手动改权重，周期以天计。PID 是**闭环控制**——系统实时感知误差、实时调整、实时反馈，周期以分钟秒计。从'人在环路里'变成'人只设目标，机器自己跑'。"

### 安全机制（面试必追问）

1. **Clipping 截断**: 限制 PID 输出最大变化幅度，防止剧烈波动
2. **KL 散度监控**: 排序打分分布偏移过大 → 自动降级回兜底策略
3. **AUC 阈值降级**: 离线 AUC 跌破安全线 → 回滚

### 结果: UV 价值 +12%

## 第二件事: Borda Count 做召回动态融合

### Borda 核心思想

把多路召回合并建模为**投票问题**：

- 每路召回源 = "投票者"
- 每个 Item = "候选人"
- Item 在某路排名越高 = 得票越多

```text
I2I 召回:   Item_A(第1名) → 100分,  Item_B(第3名) → 98分
U2I 召回:   Item_A(第5名) → 96分,   Item_C(第1名) → 100分
Embedding:  Item_B(第2名) → 99分,   Item_A(第8名) → 93分
              │
              ▼ 加权汇总（各路权重由离线评估器生成）
Item_A 总分 = w1×100 + w2×96 + w3×93 = 最高 → 排第1
```

### 为什么用 Rank 不用分数？

不同召回源分数分布完全不同（I2I在[0,1]，Embedding在[-100,100]），直接加没意义。**Rank 分布无关**，第1名就是第1名。

### 计算复杂度

纯整数加权求和，线上几十毫秒处理几千 Candidate，零压力。

### 权重怎么来？

- **离线**: 生成器(Generator)自动搜索各路最优权重
- **在线**: 评估器(Evaluator)评估不同权重的线上效果，反馈指导生成器
- 闭环: 离线生成 → 在线评估 → 反馈优化

### Borda Count vs MLP 融合的优劣

> MLP: 表达能力强但需大量数据训练、有推理延迟、不可解释
> Borda: 零训练即插即用、纯整数延迟极低、完全可解释、Rank天然归一化
> 10+路召回经常上下线，Borda 的灵活性和可维护性更重要

### 结果: GMV +2.4%

## 第三件事: 全链路评估与解耦

### Hitrate 评估

对 20+ 种召回源统一评估:

- 单路: 各路召回命中率
- 组合: 发现可互补的召回源
- 粗排一致性: 召回排序和粗排打分是否一致

### 解耦 — 最有深度的洞察

**问题本质**:

```text
精排喜欢A类 → A类曝光多 → 召回学到A是正样本 → 更多召回A
精排不喜欢B类 → B类没曝光 → 召回学不到B      → 永远不召回B
                    ↑ 马太效应 Loop ↑
```

**解法**:

1. **Exploration Traffic（随机探索流量）** 收集无偏数据——不经过精排筛选的随机曝光
2. 用无偏数据修正召回模型训练 Label
3. 召回层终于能"看到"被精排误杀的潜在好商品

面试 30 秒版:
> "推荐系统漏斗模式有经典的上下游耦合问题：召回正样本来自精排胜出日志，精排不喜欢的永远不被召回，形成马太效应。我通过 Exploration Traffic 收集无偏数据修正召回 Label，同时和精排联动对召回来源做泛化，打破这个 Loop。"

---

## 全场域优化（配套）

- **样本侧**: 缓存区归因延迟Label + 缓冲队列保持正负样本比例
  - 电商用户浏览到购买可能隔几天，当天标负样本 = Fake Negative
  - 设置归因窗口（如72小时），样本暂存等待转化信号回传
- **特征侧**: Drop Rank 选取大模型 Top 10% 特征用于 LTR = **模型蒸馏**思想
  - 大模型特征成千上万推理慢，LTR用轻量模型
  - Drop Rank 评估特征重要度（去掉某特征后排序变化），蒸馏最重要的给 LTR
- **工程侧**: 数据源 → 样本 → 训练 → 线上生效的全配置化流程
- 结果: 各场域 IPV +2%, UV 价值 +2%+
